## 二、严重问题（P0 — 必须修复）

### 2.1 MVP 必做范围膨胀失控

**现状**：原始 MVP 有 18 项必做，第一轮评审修订后增长到 **29 项**。新增项包括草稿评分、多 Agent 委派审计链路、灰度回滚、任务 token/工具调用上限、成本告警、沙盒预置场景层——每一项单独拿出来都是不小的工程量。

**风险**：文档第 22.5 节明确写了"平台过重"的风险应对是"MVP 收敛、样板场景优先、架构预留但功能不全做"，但 MVP 范围正在往反方向走。第一版做太多做不完，或者做出来每个点都打折扣。

**建议**：

MVP 必做范围砍回 3 个核心闭环，其余降级为"架构预留 + 增强版后置"：

| 闭环 | MVP 必做 | 增强版后置（第二阶段） |
|------|---------|----------------------|
| **创建发布闭环** | 一句话创建草稿 + 表单配置 + 基础沙盒验证（自动验证层） + 发布回滚 | 草稿评分与风险提示、预置场景测试层、灰度多维发布 |
| **运行执行闭环** | 单 Agent 运行 + HTTP/内置工具 + 基础重试 + 任务状态机 + Web Chat + 一个企聊渠道 | 多 Agent 协作完整链路、委派审计链路、降级/熔断/补偿策略 |
| **治理闭环** | 权限策略 + 动态授权挂起恢复 + 基础 Trace/审计 + Agent 日预算 + Prompt 版本 | 用户/部门/工具/模型多维预算、成本审计、告警降级、审批工作台 |

**关键调整**：

- **多 Agent 协作**：从"必做"改为"架构预留 + 基础 Demo 验证"——MVP 只做主 Agent 调用一个专家 Agent 的最小路径，完整委派链路、责任链、冲突处理放到第二阶段
- **灰度发布**：从"5 维灰度"降为"白名单发布 + 一键回滚"——MVP 不需要按部门、流量比例、时间窗口灰度
- **沙盒测试**：只做自动验证层，预置场景层和人工验收层放到第二阶段
- **成本控制**：只做 Agent 级日预算 + 任务 token 上限 + 基础告警，不做多维度预算和自动降级熔断
- **草稿评分**：放到第二阶段，MVP 阶段一句话创建后直接进表单配置

### 2.2 需求文档越界 —— 混入技术设计内容

**现状**：项目规范明确要求"需求文档描述'做什么'，技术文档描述'怎么做'"，"需求文档不得包含数据库表设计、接口定义、技术架构、代码结构"。但当前文档多处越界：

| 章节 | 越界内容 | 性质 | 应迁移到 |
|------|---------|------|---------|
| 7.2 对话状态展示 | 定义了具体状态流转 `理解中→计划中→执行中→等待确认/审批→完成/失败/已取消` | 状态机设计 | 技术方案的任务状态机 |
| 8.2 重试策略 | 最大次数、间隔、退避算法、重试前提示 | 实现逻辑 | 技术方案的异常处理 |
| 8.4 降级策略 | "高级模型不可用时降级到低成本模型"、"工具不可用时切换替代工具" | 技术方案 | 技术方案的降级设计 |
| 8.5 熔断策略 | "连续失败时暂停相关能力" | 基础设施设计 | 技术方案的熔断机制 |
| 14.2 权限交集 | `有效权限 = 用户权限 ∩ 主 Agent 权限 ∩ 专家 Agent 权限` | 权限算法 | 技术方案的权限模型 |
| 15.3 权限模型 | `可访问知识 = Agent 知识权限 ∩ 用户知识权限` | 权限算法 | 技术方案的权限模型 |
| 18.5 Runtime vs Workflow | "Runtime 负责决策和计划，Workflow 负责执行和状态追踪" | 架构分工 | 技术方案的架构设计 |

**判断标准**：

- ✅ "用户应能看到任务处于哪个阶段" → 这是**需求**
- ❌ "状态流转为理解中→计划中→执行中" → 这是**技术设计**
- ✅ "多 Agent 协作时不能绕过任何一方的权限" → 这是**需求约束**
- ❌ "有效权限 = 用户 ∩ 主 Agent ∩ 专家 Agent" → 这是**技术设计**

**建议**：

需求文档只保留**期望的产品行为和约束条件**。具体实现公式、状态机定义、架构分工、算法描述迁移到技术方案文档。

迁移示例：

| 原文（需求文档） | 调整后（需求文档） | 技术方案补充 |
|-----------------|------------------|------------|
| 对话状态流转为 `理解中→计划中→执行中→...` | 用户在任务执行过程中应能看到当前阶段、已完成步骤和下一步动作 | 定义具体状态机、状态转换规则和触发条件 |
| 有效权限 = 用户 ∩ 主 Agent ∩ 专家 Agent | 多 Agent 协作时，任何一方的权限不足都应阻止对应动作的执行 | 设计权限计算模型、权限缓存策略和实时校验机制 |
| 重试策略支持最大次数、间隔、退避 | 工具调用临时失败时应自动重试，重试仍失败时应告知用户并建议替代操作 | 定义重试配置参数、退避算法和降级触发条件 |

**现状**：第 3 章的 5 条信任机制与第 4 章的核心原则存在一一对应关系：

## 三、重要遗漏（P1 — 强烈建议补齐）

### 3.1 缺少多租户隔离模型

**现状**：文档定义了"平台超级管理员管理租户"，但整篇需求没有回答以下问题：

| 问题 | 说明 |
|------|------|
| 数据隔离方式 | 不同租户的数据是物理隔离（独立数据库/实例）还是逻辑隔离（共享数据库 + 租户标识）？ |
| 资源归属层级 | 工具、知识库、Prompt 模板是平台级（所有租户共享）还是租户级（各租户独立）？ |
| Agent 跨租户 | 一个企业的 Agent 能否被另一个企业使用？ |
| 配置继承 | 平台级配置和租户级配置的关系是什么？租户能否覆盖平台默认值？ |
| 模型资源 | 不同租户是否共享模型配额？如何隔离成本？ |

**建议**：

增加"多租户模型"章节，至少定义：

1. **资源归属层级**：平台级（模型、内置工具、基础 Prompt 模板）vs 租户级（Agent、自定义工具、知识库、渠道配置）vs Agent 级（角色、权限、工作流）
2. **数据隔离策略**：MVP 阶段建议逻辑隔离（共享数据库 + 租户 ID 过滤），预留物理隔离扩展能力
3. **配置继承规则**：平台默认 → 租户覆盖 → Agent 定制，三级继承
4. **跨租户共享规则**：MVP 阶段禁止跨租户共享，后续通过 Agent 市场实现受控共享

---

### 3.2 缺少 Agent 无限委派链的防护

**现状**：第 14 章描述了主 Agent 委派专家 Agent，但没有定义委派约束。在实际运行中，如果没有限制，可能出现：

- **无限深度**：Agent A → Agent B → Agent C → Agent A（循环）
- **指数爆炸**：一个 Agent 同时委派 5 个专家，每个专家又委派 5 个……
- **资源耗尽**：委派链越长，消耗的 token、时间和成本指数级增长
- **责任模糊**：5 层委派后，用户完全无法理解发生了什么

**建议**：

增加"委派约束规则"：

| 约束 | 建议值 | 说明 |
|------|-------|------|
| 最大委派深度 | 2 层 | 主 Agent → 专家 Agent，不允许专家再委派 |
| 最大委派广度 | 5 个 | 单次任务最多同时委派 5 个专家 Agent |
| 防环机制 | 去重检测 | 委派链中不允许出现同一个 Agent 两次 |
| 超限处理 | 终止并告知用户 | 超出约束时，主 Agent 终止委派并告知用户任务过于复杂，建议拆分或转人工 |
| 委派成本预估 | 委派前评估 | 委派前预估专家 Agent 的 token 和时间消耗，超出阈值时触发确认或审批 |

---

### 3.3 缺少数据隐私与保留策略

**现状**：Agent 平台会产生大量敏感数据（对话记录、任务内容、审批信息、知识库访问记录），但需求中没有定义数据隐私和保留策略。

| 遗漏点 | 风险 |
|-------|------|
| 对话数据保留时长 | 企业合规要求（金融/医疗等行业有明确保留要求） |
| 用户数据删除权 | 用户离职后，其对话和记忆如何处理？ |
| 审计日志脱敏 | 日志中出现的密码、个人身份信息、薪资等如何脱敏？ |
| Agent 记忆清理 | Agent 停用后，其记忆数据是否保留？保留多久？ |
| 知识库访问记录 | 谁在什么时间通过 Agent 访问了哪些知识，需要保留多久？ |

**建议**：

增加"数据隐私与生命周期"章节：

1. **数据分类**：将平台数据分为对话数据、任务数据、审批数据、审计日志、Agent 记忆、知识访问记录，分别定义保留策略
2. **保留策略**：每类数据定义默认保留时长，支持租户级自定义
3. **删除策略**：用户离职时自动触发数据清理（或脱敏）流程
4. **脱敏规则**：审计日志中的敏感字段（密码、身份证、薪资等）自动脱敏
5. **Agent 生命周期联动**：Agent 停用时明确其关联数据的处理方式

MVP 阶段至少需要定义：数据保留时长、用户删除权、审计日志脱敏规则。

---

### 3.4 缺少版本更新时的兼容性策略

**现状**：第 17 章描述了灰度发布机制，但只关注"如何灰度推送新版本"，没有回答一个关键问题：**Agent 版本更新后，旧版本产生的"活"数据怎么办？**

| 场景 | 问题 |
|------|------|
| 进行中的对话 | 用户正在和旧版本 Agent 聊天，新版本发布了，对话中途切换还是继续用旧版本？ |
| 进行中的任务 | 旧版本发起的多步骤任务执行到一半，新版本的 Prompt/工具/权限都变了 |
| 待审批的请求 | 基于旧版本权限策略发起的审批，审批通过后按旧版本还是新版本执行？ |
| 已配置的定时事件 | 旧版本配置的定时任务，新版本的工具或 Prompt 变了，事件触发时用哪个版本？ |
| Agent 记忆 | 旧版本积累的记忆，新版本是否继承？格式兼容吗？ |

**建议**：

在第 17 章补充版本兼容性策略：

1. **进行中对话/任务**：版本锁定——正在进行的对话和任务继续使用发起时的版本，直到完成或用户主动刷新
2. **待审批请求**：按发起时的版本执行，审批通过后不自动升级
3. **定时事件**：升级时自动迁移到新版本，迁移前做兼容性检查（工具是否存在、权限是否满足）
4. **Agent 记忆**：跨版本继承，格式不兼容时做迁移或降级处理
5. **版本回滚**：回滚不影响已完成任务的数据，只影响后续新请求

### 3.5 "一句话创建"的失败场景缺失

**现状**：第 11 章只描述了"成功生成草稿后"的质量保障（评分、理由、差异、校验），但完全没考虑创建过程中的失败场景：

| 失败场景 | 具体问题 |
|---------|---------|
| 输入太模糊 | 用户说"帮我创建一个助手" → 无法推断领域、职责和工具 |
| 能力超出范围 | 用户说"创建一个可以自动交易的 Agent" → 平台当前不支持 |
| 安全红线 | 用户说"创建一个可以查看所有人薪资的 Agent" → 违反权限原则 |
| AI 生成失败 | 模型服务不可用或返回异常 → 无法生成草稿 |
| 描述自相矛盾 | 用户说"创建一个只读的 Agent，但可以修改和删除数据" → 配置冲突 |

**建议**：

第 11 章补充"创建失败与异常处理"：

1. **输入不足时**：系统识别关键信息缺失，向用户追问补充（如"请问这个数字员工主要负责哪个业务领域？"）
2. **能力超出范围时**：明确告知用户当前平台不支持该能力，建议相近的替代方案
3. **安全红线时**：直接拦截，说明违反的安全策略，不允许继续创建
4. **AI 生成失败时**：提供从模板创建或空白配置创建的降级入口
5. **描述矛盾时**：识别矛盾点，让用户确认或选择

## 四、设计优化（P2）

### 4.1 成本控制对 MVP 过重

**现状**：第 9 章定义了 6 个预算维度（Agent/用户/部门/任务/工具/模型）× 7 种保护策略（拒绝/降级模型/降级工具/压缩上下文/暂停/审批/熔断），加上成本展示和成本审计。这是一个完整的 FinOps 平台。

**建议**：

第 9 章的内容保留作为演进目标，但在 MVP 范围中做明确分层：

| 维度 | MVP | 第二阶段 | 第三阶段 |
|------|-----|---------|---------|
| Agent 级预算 | ✅ 日/月 token 预算 | ✅ 调用次数、费用上限 | ✅ 智能预算建议 |
| 用户级预算 | ❌ | ✅ 高频调用限制 | ✅ 个性化配额 |
| 部门级预算 | ❌ | ❌ | ✅ 部门成本归属 |
| 任务级限额 | ✅ 单次 token 上限 | ✅ 步骤数、工具调用数 | ✅ 动态调整 |
| 工具级预算 | ❌ | ✅ 收费 API 限额 | ✅ 工具成本优化 |
| 模型级预算 | ❌ | ✅ 高成本模型限制 | ✅ 智能路由降级 |
| 保护策略 | ✅ 拒绝 + 基础告警 | ✅ 降级 + 熔断 | ✅ 自动审批 |
| 成本审计 | ❌ | ✅ 基础审计 | ✅ 完整 FinOps |

### 4.2 权限模型需要支持委派授权

**现状**：权限交集公式 `有效权限 = 用户权限 ∩ 主 Agent 权限 ∩ 专家 Agent 权限` 是严格交集，意味着有效权限永远是最受限的那个。

**问题**：实际业务中存在需要"临时扩大权限"的场景。例如：

> 项目助理（主 Agent）需要调用财务 Agent 查询项目预算。财务 Agent 本身没有这个项目的数据权限，但主 Agent 可以在这次委派中临时授予"仅限查看项目 X 的预算"的权限。

严格交集模型下，这种合法的业务场景无法实现。

**建议**：

权限模型需要支持两种模式：

1. **默认模式（严格交集）**：大多数场景使用，取三方权限交集
2. **委派授权模式**：主 Agent 可以在委派时授予专家 Agent 限定范围的额外权限，该权限仅在本次任务中生效，且有明确的范围、时间和审计记录

委派授权需要满足以下约束：

- 主 Agent 只能授予自己拥有的权限（不能凭空创造权限）
- 授权范围必须明确限定（具体资源、具体操作、具体时间）
- 每次委派授权都记录审计日志
- 高风险授权仍需走审批流程

---

### 4.3 缺少 Agent 发现与注册机制

**现状**：第 14 章描述了主 Agent 委派专家 Agent，第 18.8 节提到了 Multi-Agent Coordinator，但都没有回答一个前提问题：**主 Agent 怎么知道有哪些专家 Agent 可以委派？**

| 问题 | 说明 |
|------|------|
| Agent 目录 | 有没有统一的 Agent 注册中心？ |
| 能力描述 | 专家 Agent 如何描述自己能处理什么类型的任务？ |
| 自动匹配 | 主 Agent 是自动发现合适的专家，还是需要管理员预先配置协作关系？ |
| 可见性控制 | 不同租户、不同部门的 Agent 互相可见吗？ |
| 调用条件 | 专家 Agent 是否定义了调用前置条件（如需要的最小权限、支持的输入格式）？ |

**建议**：

在功能范围中增加 Agent Registry / Agent Search 机制：

1. **Agent 注册**：每个 Agent 发布时注册自己的能力描述、适用场景、输入输出格式、调用条件和成本预估
2. **Agent 检索**：主 Agent 通过任务类型、能力需求检索匹配的专家 Agent
3. **可见性控制**：专家 Agent 的可见范围可配置为租户内、部门内或指定 Agent
4. **调用条件检查**：委派前自动检查专家 Agent 的前置条件（权限、输入格式、可用状态）

MVP 阶段可以用简单的"管理员配置协作关系"代替自动发现，但架构上需要预留 Agent Registry 的扩展能力。
