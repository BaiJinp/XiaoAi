# 企业数字员工平台产品设计评审报告

> 评审人：资深产品经理（企业 Agent 设计方向）
> 评审对象：`docs/req/20260604_企业数字员工平台_需求.md`
> 评审日期：2026-06-05
> 评审结论：**方向正确、架构前瞻、但在产品体验和失败处理两个维度存在明显短板**

---

## 一、总体评价

产品设计在"平台能力"维度覆盖全面，模块划分清晰，核心原则（配置优先、边界自治、动态授权、多 Agent 受控协作）方向正确。

但 Agent 产品的本质不是能力堆叠，而是**让用户在不确定的环境中建立信任**。信任来自四个方面：

1. **一致的行为** —— Agent 在不同渠道、不同场景下表现可预期
2. **可控的边界** —— 用户和管理员清楚 Agent 能做什么、不能做什么
3. **透明的决策** —— Agent 为什么这样做，能被追溯和理解
4. **优雅的错误处理** —— 出错时不是崩溃，而是可理解的降级和恢复

当前需求文档在 1、4 两点上覆盖不足。

---

## 二、严重缺陷（P0 — 必须补齐）

### 2.1 缺少「失败路径」设计

**问题**：整个需求文档只描述了正常流程（创建→配置→测试→发布→运行），但企业级 Agent 的真实场景中，**80% 的工程复杂度在异常分支**。

以下关键异常场景在需求中完全未涉及：

| 异常场景 | 具体问题 |
|---------|---------|
| 工具调用失败 | 超时/报错后怎么办？重试？降级？通知用户？重试几次？ |
| 任务拆解出错 | Agent 拆出不合理的子任务，如何检测和纠正？ |
| 多 Agent 结论冲突 | 专家 Agent 返回矛盾结论，主 Agent 如何仲裁？ |
| 审批被拒绝 | 任务是回滚到上一步？走替代路径？还是直接终止？ |
| 知识召回质量差 | 检索结果偏离导致回答错误，如何检测和纠正？ |
| 模型输出异常 | 返回格式不符预期（tool_call 参数错误），怎么兜底？ |
| 外部服务不可用 | 知识库、模型服务、工具服务宕机时的降级策略？ |
| 并发冲突 | 多个用户同时给同一 Agent 下达冲突任务怎么处理？ |

**建议**：

在需求文档中增加「异常场景与降级策略」章节，每个核心场景都要有对应的失败处理策略。遵循 **"failure-first design"** 原则 —— 先设计失败怎么处理，再设计成功怎么走。

需要定义的关键策略：
- **重试策略**：哪些操作可重试、重试次数、重试间隔、退避算法
- **降级策略**：主路径失败后的备选路径（如工具失败 → 告知用户并建议替代操作）
- **熔断策略**：连续失败多少次后暂停相关能力
- **超时策略**：各类操作的超时阈值和超时后的行为
- **补偿策略**：部分完成的任务如何回滚或补偿

---

### 2.2 缺少「对话体验设计」

**问题**：需求中描述了大量平台后端能力（Runtime、Workflow、Permission、Audit……），但对终端用户和数字员工的**交互体验几乎没有描述**。

Agent 产品 = 交互设计，不是后端 API。以下问题在需求中未定义：

| 体验维度 | 具体问题 |
|---------|---------|
| 消息呈现 | 用户看到什么？纯文本？卡片？富文本？文件？ |
| 确认交互 | Agent 需要用户确认时，是卡片按钮？文字回复？弹窗？ |
| 进度感知 | Agent 长时间执行任务时，用户如何感知进度？进度条？阶段通知？沉默执行？ |
| 打断机制 | 用户如何打断正在执行的任务？打断后任务怎么处理？ |
| 多轮上下文 | 对话窗口长度策略？超出后如何截断或摘要？ |
| 质量反馈 | 用户如何评价 Agent 回复？点赞/踩？评分？文字反馈？ |
| 错误展示 | Agent 出错时，用户看到什么？（不能暴露技术细节，但需要有用信息） |
| 渠道适配 | 同一 Agent 在飞书群聊 vs 单聊 vs Web Chat 的交互是否不同？ |

**建议**：

增加「用户交互体验规范」章节，至少覆盖以下内容：

1. **消息类型定义**：文本、卡片（结构化信息展示）、文件、确认框、进度条、错误提示
2. **对话状态展示规范**：思考中 → 执行中 → 等待确认 → 完成/失败，每个状态的用户可见信息
3. **打断机制**：用户发送新消息时的冲突处理策略
4. **反馈收集机制**：每次交互后的评价入口和收集策略
5. **渠道适配规则**：不同渠道的消息类型映射和降级策略

---

### 2.3 缺少「成本控制」闭环

**问题**：需求中只提到了成本「统计」，但没有成本「控制」机制。统计是事后看，控制是事前管。企业场景下，**成本失控是平台被停用的首要原因**。

| 成本风险 | 具体问题 |
|---------|---------|
| 单次对话超限 | 一次对话消耗大量 token（如反复调用工具），怎么控制？ |
| Agent 预算 | 单个 Agent 日/月消耗预算如何设定？超了怎么办？ |
| 用户滥用 | 用户频繁调用高成本 Agent（反复生成报告），谁控制？ |
| 工具调用费用 | 调用外部 API 按次收费，费用怎么管控和归属？ |
| 模型降级 | 预算不足时，是拒绝服务、降级到低成本模型、还是通知管理员？ |

**建议**：

成本控制需要从「统计」升级为完整闭环：

```
预算设定 → 限额控制 → 实时告警 → 自动降级 → 熔断保护 → 超支审计
```

具体机制：
- **Agent 预算**：每个 Agent 可设定日/月 token 预算和调用次数上限
- **对话级限流**：单次对话 token 上限，超出后 Agent 主动压缩上下文或终止
- **工具调用预算**：按工具设定调用频次上限和费用上限
- **告警机制**：预算使用达 80% 告警 Agent 管理员，100% 触发保护策略
- **降级策略**：超预算后可配置为：拒绝服务 / 降级模型 / 降级工具 / 通知管理员审批
- **费用归属**：支持按 Agent、按部门、按用户的费用分摊和统计

## 三、重要隐患（P1 — 强烈建议补齐）

### 3.1 「一句话创建 Agent」的质量保障

**问题**：用户输入一句话生成 Agent 草稿，方向正确，但缺少质量保障：

- 生成的草稿质量参差不齐，管理员审核成本可能很高
- 不同用户描述同一个 Agent，生成的配置差异很大，如何保持一致性？
- 管理员怎么判断 AI 生成的配置是否合理？（他自己可能也不专业）

**建议**：

- **引入配置评分机制**：系统自动评估草稿的完整性、风险等级、最佳实践匹配度，给出评分和修改建议
- **提供配置差异对比**：让管理员看到默认值和 AI 建议值的区别，突出变更项
- **加入建议理由**：每个建议配置都附带"为什么这样配"，降低审核认知成本
- **配置校验清单**：发布前系统自动检查必填项、冲突项、风险项，生成检查报告

---

### 3.2 多 Agent 协作的「责任归属」未定义

**问题**：需求中说"主 Agent 汇总并对最终交付负责"，但缺少具体定义：

- 专家 Agent 返回错误信息导致主 Agent 做出错误决策，责任归谁？
- 专家 Agent 有自己的权限配置，是否可能越权？主 Agent 是否要二次校验？
- 审计日志中，多 Agent 调用链路如何追踪和回溯？
- 用户投诉时，是投诉主 Agent 还是背后的专家 Agent？

**建议**：

明确定义「责任链模型」：

- **主 Agent 对外负总责**：无论内部如何委派，对外只看到主 Agent
- **内部调用链追踪**：每次委派记录委派原因、委派上下文快照、返回结果、风险评估
- **权限二次校验**：主 Agent 委派时，使用「主 Agent 权限 ∩ 专家 Agent 权限 ∩ 用户权限」的交集
- **审计链路完整**：一次用户请求 → 主 Agent 决策 → 委派记录 → 专家 Agent 执行 → 结果返回 → 主 Agent 汇总，全链路可追溯

---

### 3.3 「沙盒测试」定义模糊

**问题**：需求中提到沙盒测试，但缺少关键定义：

- 测试用例从哪来？谁写？
- 测试覆盖什么维度？
- 测试通过/不通过的标准是什么？
- 测试环境如何隔离？

**建议**：

沙盒测试至少需要三层：

| 层级 | 内容 | 执行方式 |
|------|------|---------|
| **自动验证层** | 配置完整性检查、权限冲突检测、Prompt 安全校验、工具可用性验证 | 系统自动执行 |
| **预置场景层** | 边界测试（超出职责范围的请求）、注入测试（恶意 Prompt）、权限测试（越权请求）、成本测试（高消耗场景） | 平台提供标准场景 |
| **人工验收层** | 管理员用真实话术测试，系统记录对话 | 人工操作 |

额外要求：
- 人工验收的对话记录自动转化为回归测试用例
- 沙盒环境使用脱敏数据，与生产环境严格隔离
- 测试结果生成报告，包含功能覆盖度、风险点、成本预估

---

### 3.4 知识库绑定模型不清晰

**问题**：需求中说「绑定知识库」，但以下问题未定义：

| 问题 | 说明 |
|------|------|
| 绑定数量 | 一个 Agent 可以绑多个知识库吗？ |
| 优先级 | 多个知识库时，检索优先级怎么定？ |
| 生效机制 | 知识库更新后，Agent 什么时候生效？实时？需要重新发布？ |
| 权限层级 | 不同 Agent 绑同一个知识库时，权限按 Agent 还是按用户控制？ |
| 质量兜底 | 检索召回率/准确率不达标时，Agent 怎么处理？ |

**建议**：

明确知识库绑定模型：

- **绑定关系**：支持 1 Agent : N 知识库，每个知识库可设权重/优先级
- **生效策略**：知识库更新后，Agent 配置缓存刷新机制（实时/定时/手动刷新）
- **权限模型**：知识库访问权限 = Agent 权限 ∩ 用户权限，两者都满足才可访问
- **质量兜底**：检索置信度低于阈值时，Agent 明确告知用户"未找到可靠信息"而非编造答案

## 四、设计优化建议（P2）

### 4.1 Agent 人设一致性规范

**问题**：需求中提到「角色」「职责」「回复风格」，但在企业场景中，Agent 的行为一致性直接影响用户信任。

**建议**：

增加「Agent 人设规范」章节，定义：

- **跨渠道一致性**：同一 Agent 在不同渠道（飞书群聊 vs 单聊 vs API）的核心人设不变，但交互形式可适配
- **跨会话一致性**：同一用户隔段时间再找同一 Agent，Agent 应体现记忆连续性（基于会话记忆）
- **企业品牌约束**：Agent 的语言风格应符合企业品牌调性，可设定企业级人设基线
- **角色边界一致性**：超出职责范围的请求，Agent 必须明确拒绝并说明原因，不得越界

---

### 4.2 动态审批的产品体验细化

**问题**：动态审批的架构设计（策略路由、聚合、分级）完整，但产品层面缺少前台设计。

**建议**：

补充动态审批的前台产品设计：

| 产品要素 | 定义 |
|---------|------|
| **审批工作台** | 独立的审批管理界面，按紧急度/Agent/时间排序 |
| **审批超时策略** | 可配置：自动拒绝 / 升级上级 / 继续等待（带最大等待时间） |
| **批量审批** | 支持同类审批一键批量通过/拒绝 |
| **拒绝反馈** | 审批拒绝后，Agent 收到拒绝原因，转为告知用户并建议替代操作 |
| **审批通知** | 按渠道（飞书/钉钉/邮件）推送审批通知，支持免打开直接审批 |
| **审批统计** | 按审批人、Agent、时间维度统计审批量、通过率、平均响应时间 |

---

### 4.3 灰度发布机制细化

**问题**：Agent 有状态（对话历史、任务状态），灰度发布比传统软件复杂，但需求中只有一句话提到。

**建议**：

明确灰度发布机制：

| 要素 | 定义 |
|------|------|
| **灰度维度** | 支持按用户白名单、按部门、按流量百分比灰度 |
| **版本隔离** | 灰度版本和正式版本的配置、Prompt、工具版本独立 |
| **状态兼容** | 灰度版本的 Agent 接管已有会话时，需兼容历史状态 |
| **回滚机制** | 一键回滚到上一版本，灰度期间的数据保留策略 |
| **灰度指标** | 自动采集灰度期间的对话质量、错误率、成本、用户反馈 |
| **全量判断** | 灰度指标达标后，系统建议全量发布；异常则自动告警 |

---

### 4.4 Agent Runtime 与 Workflow Engine 边界

**问题**：同时设计了 Agent Runtime（意图识别、任务拆解、工具选择）和 Task & Workflow Engine（状态机、DAG、审批节点），但职责边界不清晰。

**建议**：

采用 **"Runtime 决策，Workflow 执行"** 模式：

```
用户请求
   ↓
Agent Runtime（推理层）
   ├── 意图识别
   ├── 任务分解决策
   ├── 工具选择决策
   └── 输出：执行计划（DAG 草稿）
   ↓
Task & Workflow Engine（执行层）
   ├── 接收执行计划
   ├── 状态机驱动执行
   ├── 审批节点挂起/恢复
   ├── 超时/重试处理
   └── 输出：执行结果 + 状态追踪
```

关键规则：
- Runtime 只做决策，不做状态管理
- Workflow 只做执行，不做智能决策
- Runtime 可以在执行中根据中间结果调整后续计划（动态规划）
- 两层之间的接口是「执行计划」和「执行反馈」

---

### 4.5 模型网关与 Prompt 治理解耦

**问题**：模型网关（路由、限流、降级）和 Prompt 治理（版本、测试、A/B）的关注点不同，放在同一模块会增加耦合。

**建议**：

- **模型网关**作为独立基础设施层：负责模型路由、负载均衡、限流降级、成本统计、调用审计
- **Prompt 治理**作为业务应用层：负责 Prompt 版本管理、A/B 测试、安全检查、效果评估
- 两者通过标准接口交互：Prompt 治理决定"用什么 Prompt"，模型网关决定"调哪个模型实例"

## 六、评审总结

### 做得好的地方

1. **产品定位清晰**："数字员工"的产品心智比"AI 助手"或"聊天机器人"更适合企业场景
2. **核心原则正确**：配置优先、边界自治、动态授权、受控协作 —— 每一条都经得起推敲
3. **模块划分全面**：12 个功能模块覆盖了 Agent 平台的主要维度
4. **MVP 范围合理**：有明确的做/不做边界，样板场景选得好（项目助理）
5. **架构前瞻性**：MCP、动态审批、可插拔存储等设计为后续演进留了空间

### 需要补齐的地方

1. **从"系统能力"转向"用户体验"**：当前需求像后端架构文档，缺少终端用户视角
2. **从"Happy Path"转向"Full Path"**：补充失败场景、异常处理、降级策略
3. **从"统计看板"转向"控制闭环"**：成本、质量、风险都需要从"能看"升级为"能管"
4. **从"能力描述"转向"机制定义"**：沙盒测试、知识库、灰度发布等需要具体机制而非一句话提及

### 一句话总结

> 你的产品设计在"平台能力"维度很完整，但在"产品体验"和"失败处理"两个维度有明显短板。Agent 产品的本质不是能力堆叠，而是**让用户在不确定的环境中建立信任**。
