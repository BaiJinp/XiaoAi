# 项目助理 Agent MVP / 企业数字员工平台演进需求文档

## 1. 产品定位

当前阶段的交付目标不是先建设完整企业数字员工平台，而是先做出一个真正好用的项目助理 Agent。项目助理 Agent 需要面向真实项目工作，通过自然语言接收复杂目标，连接项目知识、资料、工具和审批流程，帮助用户完成会议纪要转任务、项目周报、风险分析、知识问答和可复用交付物生成。

本产品不是单个聊天机器人，也不是传统流程编排平台。它的产品路径是 Agent-first、Platform-ready：先把一个项目助理 Agent 做到可用、可靠、可解释、可恢复，验证用户是否愿意把真实工作交给它；同时保留身份、工具、任务、权限、审计、成本、Runtime 管控等平台化边界，使后续可以扩展为企业级数字员工平台。

当前阶段以“项目助理 Agent first，平台化能力后延”为目标。平台化能力不是取消，而是先作为支撑项目助理 Agent 的最小护栏和架构预留，不作为当前产品交付主线。需求文档只描述产品需要支持的行为、边界和约束；具体状态机、权限计算、架构分层、接口、数据库和实现策略放到后续技术方案中设计。

## 2. 产品目标

- 支持一个项目助理 Agent 完成真实项目工作，包括理解目标、必要澄清、查询项目知识、读取资料、调用受控工具、生成交付物和自检结果。
- 支持项目助理核心场景：会议纪要转行动项/任务草稿、项目周报生成、项目风险分析、项目知识问答和高风险动作审批恢复。
- 支持任务执行过程可见，让用户看到计划、阶段进度、知识依据、工具动作、等待事项、不确定点、失败原因和下一步可选操作。
- 支持输出可直接复用的交付物，包括结构化周报、行动项清单、风险清单、建议动作和可复制的 Markdown 内容。
- 支持项目助理 Agent 的最小配置能力，包括角色职责、知识范围、工具范围、基础权限、基础预算和试用范围。
- 支持权限不足或高风险动作时发起动态审批，审批通过后继续处理，审批拒绝或超时时给出可理解反馈。
- 支持失败路径设计，覆盖任务创建失败、工具失败、审批拒绝、知识低可信、外部服务不可用、任务取消等场景。
- 支持基础成本和边界控制，防止单个 Agent 或单次任务成本失控、权限越界或无限执行。
- 平台化能力作为后续方向保留：多租户治理、完整 Agent 版本发布、完整权限/审计/成本后台、多领域 Agent 模板、全渠道接入、多 Agent 协作、MCP/HTTP/OpenAPI 工具生态等能力不作为当前阶段交付主线。

## 3. 核心原则

企业 Agent 的核心不是“后台配置完整”，而是“用户愿意把真实工作交给它”。平台围绕以下核心原则设计。

### 3.1 行为一致

同一个 Agent 在不同渠道、不同会话、不同任务中的角色、职责、语气和边界应保持一致。渠道可以影响消息展现形式，但不应改变 Agent 的核心职责和行为边界。

### 3.2 边界可控

管理员需要清楚配置 Agent 能做什么、不能做什么、哪些动作需要确认、哪些动作需要审批、哪些动作禁止执行。普通用户在交互中也应理解 Agent 当前是否能处理请求，以及不能处理的原因。

### 3.3 决策透明

Agent 的关键动作应可解释、可追溯。用户需要看到业务可理解的说明，例如为什么需要确认、为什么等待审批、为什么无法继续。管理员和审计人员需要看到更完整的操作记录。

### 3.4 失败可恢复

Agent 出错时不能只返回“系统异常”。平台需要说明失败发生在哪个环节、是否已产生影响、用户可以重试、取消、修改、转人工还是等待恢复。

### 3.5 成本可预期

企业需要能设置基础预算和上限，避免 Agent 在长任务、重复调用、异常重试中产生不可控成本。成本能力按阶段建设，MVP 只做必要控制，不建设完整 FinOps 平台。

### 3.6 配置优先

创建数字员工优先通过自然语言、模板和表单配置完成。只有通用配置无法满足时，才进入扩展开发或定制能力接入。

### 3.7 人配置边界，Agent 自主工作

人负责配置角色、职责、权限、工具、知识、成本和风险边界；Agent 在边界内自主处理任务。人不参与每一步普通任务拆解，但在高风险、缺信息、越权、冲突和失败场景中介入。

### 3.8 企业级可治理

权限、审计、成本、风险、版本、发布、回滚、数据保留和生命周期管理必须作为平台化演进的基础能力，但在 MVP 阶段应服务于 Agent 可执行闭环，不能喧宾夺主。

## 4. 目标用户

### 4.1 当前阶段核心用户

- 普通员工：在 Agent Workbench 或企业聊天入口中提交会议纪要、项目资料、项目问题和周报/风险分析请求，查看任务进展，处理确认、审批和反馈。
- 项目负责人/业务负责人：使用项目助理 Agent 推进项目跟踪、风险识别、行动项整理和周报输出，并审批高风险动作或业务边界不明确的操作。
- 轻量 Agent 管理员：维护项目助理 Agent 的角色职责、知识范围、工具范围、基础权限、基础预算和试用范围，确保项目助理 Agent 能稳定服务当前项目工作。

### 4.2 后续平台化用户

- 平台超级管理员：后续管理租户、平台级模型、全局安全策略、基础能力、平台默认配置和系统运行。
- 企业管理员：后续管理企业组织架构、成员、企业权限、租户级配置、渠道接入、企业工具接入、数据保留策略和预算策略。
- 审计/安全人员：后续查看更完整的 Agent 行为记录，审计权限访问、审批、数据访问、异常失败、成本异常和风险事件。

MVP 阶段不围绕完整平台管理角色建设产品面，只保留支撑项目助理 Agent 安全运行所需的最小治理能力。

## 5. 核心使用场景

### 5.1 项目助理 Agent 处理复杂任务

普通员工在 Web Chat 或企业聊天工具中向项目助理 Agent 发起复杂任务，例如：根据本周会议纪要、项目资料和任务状态，生成项目周报，识别延期风险，并给出下周行动建议。

Agent 应先理解目标、明确交付物和约束，再根据任务复杂度选择执行方式。简单问题直接回答；中等任务由单 Agent 规划并调用知识或工具；复杂任务进入 Dynamic Workflow 执行模式，拆解为多个可追踪步骤，必要时并行检索资料、调用工具、生成中间结果、进行自检和汇总。

任务执行过程中，用户应能看到 Agent 正在做什么、已经完成什么、还在等待什么、哪些信息不确定、是否需要用户确认。最终结果应是可直接使用的交付物，而不是只返回过程说明。

### 5.2 会议纪要转任务

用户提交会议文本、语音转写结果或会议纪要草稿后，Agent 应提取会议结论、行动项、责任人、截止时间、风险点和待确认事项。

当责任人、时间或任务边界不明确时，Agent 应追问或标记为待确认；当已接入项目管理工具时，Agent 可在用户确认后创建或更新任务，并展示执行结果。

### 5.3 项目周报生成

用户要求生成项目周报时，Agent 应结合项目资料、任务状态、会议结论、延期记录和用户补充信息，生成结构化周报。

周报应至少包括本周进展、关键成果、延期或阻塞、风险与原因、下周计划、需要协调的事项。对来源不足或判断不确定的内容，Agent 应明确标注。

### 5.4 项目风险分析

用户要求分析项目风险时，Agent 应读取项目资料、任务状态、历史会议和相关知识，识别进度、范围、资源、依赖、质量和沟通风险。

风险输出应包含风险描述、依据、影响范围、严重程度、建议动作和需要用户确认的信息。复杂风险分析可进入 Dynamic Workflow，由 Agent 分阶段收集证据、归纳风险、交叉检查和生成建议。

### 5.5 项目助理 Agent 最小配置

轻量 Agent 管理员输入自然语言，例如：创建一个项目助理 Agent，负责项目任务拆解、会议纪要、延期提醒和周报生成。

系统生成项目助理 Agent 草稿，管理员通过最小表单继续确认角色、职责、边界、知识范围、工具范围、基础权限、基础预算和试用范围。配置完成后经过基础验证，发布给指定用户试用，验证稳定后再扩大使用范围。

MVP 阶段只要求支持项目助理 Agent 的最小配置，不追求完整多领域 Agent 创建平台。多领域模板、复杂发布、灰度、运营能力和模板市场后续建设。

### 5.6 使用数字员工处理普通任务

普通员工在 Web Chat 或企业聊天工具中发起任务。Agent 根据职责范围理解请求，必要时查询知识、调用工具、请求确认或发起审批，并向用户返回结果。

当任务耗时较长、等待审批、遇到失败或需要用户补充信息时，Agent 应给出可理解的状态提示和下一步选择。

### 5.7 动态授权

当 Agent 处理任务时发现当前权限不足，平台需要判断该动作是否允许申请授权。允许时，Agent 发起审批并暂停受限动作；审批通过后继续处理；审批拒绝、超时或不允许申请时，Agent 应告知用户原因并提供可选替代路径。

### 5.8 知识问答与知识可信

Agent 可以绑定企业知识库并基于知识回答问题。回答应尽量展示来源或依据。当未找到可靠信息、知识冲突或用户无权访问相关知识时，Agent 应明确说明，而不是编造答案。

### 5.9 后续场景展望

#### 5.9.1 多 Agent 协作

复杂任务后续可由主 Agent 委派给专家 Agent 协作完成。MVP 阶段只允许在项目助理 Agent 内部验证一个专家 Agent 的最小协作路径，用于证明复杂任务可扩展，不作为第一阶段核心交付闭环。完整责任链、冲突仲裁、自动发现和委派授权后续阶段建设。

#### 5.9.2 事件触发

业务系统事件、定时事件、审批超时、任务延期、文档更新等后续可触发 Agent 主动工作。MVP 阶段只保留能力设计入口，不建设复杂事件驱动自治。

## 6. 多租户与资源归属

平台需要支持多个企业租户使用。不同租户之间的数据、Agent、知识库、自定义工具、渠道配置、审批记录、审计记录和成本数据必须隔离，不能互相访问。

资源归属分为三类：

- 平台级资源：平台统一提供的基础模型、内置工具、基础模板、默认安全策略和公共能力。
- 租户级资源：企业自己的 Agent、自定义工具、知识库、渠道配置、组织架构、审批策略、数据保留策略和预算策略。
- Agent 级资源：某个数字员工的角色、职责、边界、知识绑定、工具绑定、权限、预算、Prompt、发布范围和运行记录。

平台默认配置可以作为租户初始化配置。租户管理员可在允许范围内覆盖平台默认配置。Agent 管理员可在租户策略范围内做 Agent 级配置。

MVP 阶段禁止跨租户共享 Agent、知识库和自定义工具。后续如建设 Agent 市场或模板市场，需要通过审批、授权、脱敏和审计实现受控共享。

## 7. Agent 创建与发布

当前阶段只做项目助理 Agent 的最小创建、配置和试用闭环。通用多领域 Agent 创建平台、模板市场、复杂发布治理和运营后台后续建设。

### 7.1 创建方式

平台长期支持以下创建方式：

- 一句话创建：用户用自然语言描述想要的数字员工，系统生成草稿。
- 模板创建：从平台或租户提供的岗位模板创建。
- 空白创建：从空白表单开始配置。

MVP 优先支持项目助理 Agent 的一句话创建草稿和最小表单配置。

### 7.2 草稿生成范围

一句话创建应生成可编辑草稿，范围包括：

- Agent 名称和角色描述；
- 主要职责；
- 不应处理的事项；
- 推荐知识库；
- 推荐工具；
- 权限建议；
- 渠道建议；
- 基础预算建议；
- 发布前待确认项。

草稿只是建议，发布前必须由 Agent 管理员确认。

### 7.3 表单配置

Agent 管理员可以通过表单修改项目助理 Agent 的角色、职责、边界、知识、工具、基础权限、基础预算和试用范围。

表单需要提示必填项、冲突项、风险项和缺失项。MVP 阶段只做项目助理 Agent 必需的基础校验；通用多领域配置、草稿评分、风险评分和最佳实践评分后续阶段建设。

### 7.4 发布验证

Agent 发布前必须经过基础验证。MVP 阶段至少验证配置完整性、必要权限、工具可用性、知识绑定有效性和 Prompt 版本存在。

预置场景测试、人工验收记录转回归用例、复杂风险测试后续阶段建设。

### 7.5 发布、白名单与回滚

MVP 阶段只要求支持项目助理 Agent 的试用范围和最小发布边界，确保指定用户可以使用稳定版本。完整白名单治理、一键回滚、按部门/流量比例/时间窗口灰度和运营能力后续阶段建设。

## 8. 一句话创建的异常处理

一句话创建是核心入口，必须处理失败和不确定场景。

### 8.1 输入信息不足

当用户输入过于模糊，例如“帮我创建一个助手”，系统应识别关键信息不足，并追问业务领域、目标用户、主要职责或使用渠道，而不是直接生成低质量 Agent。

### 8.2 能力超出范围

当用户希望创建当前平台不支持的 Agent，例如需要高度专业化自动决策或外部高风险执行能力时，系统应明确说明当前不支持，并建议可替代的低风险能力或人工流程。

### 8.3 触碰安全红线

当用户请求创建明显越权、违法、违规或高风险 Agent 时，系统应拦截创建流程，说明违反的安全或权限原则，并禁止继续发布。

创建时安全红线只解决 Agent 创建阶段的问题。Agent 运行过程中，平台也需要防止用户通过对话、文件、链接、知识文本等外部输入绕过 Agent 的角色、职责、权限和系统边界。

### 8.4 描述自相矛盾

当用户描述中存在明显冲突，例如“只读 Agent，但可以修改和删除数据”，系统应指出矛盾点，让用户选择或修正。

### 8.5 草稿生成失败

当 AI 生成草稿失败或服务不可用时，平台应提供模板创建、空白创建或稍后重试入口，避免用户卡死在创建流程。

## 9. 用户交互体验

### 9.1 消息类型

平台需要支持多种用户可理解的消息形态，并在不同渠道中适配：

- 文本消息：用于普通回答、解释、总结和失败说明。
- 卡片消息：用于任务计划、执行结果、确认、审批和结构化信息展示。
- 确认消息：用于高风险动作、执行前确认和任务取消。
- 进度消息：用于长任务、等待审批、等待外部系统和阶段性结果。
- 文件消息：用于会议纪要、报告、导出结果等交付物。
- 反馈消息：用于收集点赞、点踩、评分和文字反馈。

### 9.2 任务过程可见

用户在任务执行过程中应能看到当前阶段、已完成事项、正在等待什么、下一步可能发生什么，以及自己可以执行的操作。

平台不应向普通用户暴露技术日志、异常堆栈、密钥、内部系统细节或无意义错误码。

### 9.3 确认与取消

当 Agent 准备执行高风险动作、外部系统写操作、成本较高任务或不可轻易撤销动作时，应请求用户确认或发起审批。

用户应能取消正在处理的任务。取消后，Agent 需要说明已完成部分、未完成部分、是否产生外部影响，以及是否需要后续处理。

### 9.4 错误展示

Agent 出错时，应展示业务可理解的失败原因、影响范围和可选下一步。常见下一步包括重试、修改输入、取消任务、等待恢复、转人工、联系管理员或使用替代路径。

### 9.5 渠道适配

同一 Agent 在不同渠道中的核心职责和边界一致，但消息形态可以不同。Web Chat 支持完整交互；企业聊天工具支持简化卡片和通知；群聊中涉及敏感信息时应转入私聊、审批或 Web 页面处理；Open API 返回结构化结果供调用方展示。

### 9.6 反馈收集

关键回答和任务完成后应提供反馈入口。反馈用于 Agent 运营、知识优化、Prompt 优化、问题追踪和后续测试集建设。

## 10. 任务执行与失败处理

平台必须设计成功路径和失败路径。核心要求是：任务失败时用户能理解、能选择、能恢复或能转交。

### 10.1 任务复杂度分层

Agent 应根据用户目标、输入资料、所需工具、执行时长、风险等级和交付物要求判断任务复杂度，并选择合适的执行方式。

| 任务类型 | 执行方式 | 示例 |
|---|---|---|
| 简单任务 | 直接回答或一次知识查询 | 查询项目制度、解释文档片段、回答单点问题 |
| 中等任务 | 单 Agent 规划并调用知识或工具 | 生成会议纪要、拆解任务建议、查询项目状态 |
| 复杂任务 | Dynamic Workflow | 项目周报生成、项目风险分析、跨资料需求整理、复杂方案生成 |

复杂度判断不应向用户暴露为技术分类，但应影响任务执行过程展示、成本提示、确认要求和失败恢复方式。

### 10.2 Dynamic Workflow 执行模式

Dynamic Workflow 是复杂任务的内部执行模式，不是面向用户的流程画布，也不是默认对所有请求启用的大规模多 Agent 协作。

当任务进入 Dynamic Workflow 时，Agent 应完成以下行为：

1. 明确任务目标、输入、约束、交付物和验收标准。
2. 生成可理解的执行计划，并在必要时让用户确认方向。
3. 将复杂任务拆解为若干可追踪步骤。
4. 根据步骤需要查询知识、读取资料、调用工具、生成中间结果或请求用户补充信息。
5. 对中间结果进行合并、去重、冲突识别和不确定性标注。
6. 对最终结果进行自检，确认是否覆盖用户目标和交付要求。
7. 输出可直接使用的交付物，并说明依据、风险、待确认事项和下一步建议。

MVP 阶段 Dynamic Workflow 优先服务项目助理 Agent 的复杂任务，不建设通用可视化 Workflow 编排器，不开放用户自定义复杂流程，不建设大规模 Swarm。

### 10.3 Dynamic Workflow 边界

Dynamic Workflow 必须有明确边界，避免复杂任务失控。

- 有界执行：限制最大步骤数、最大子任务数、最大执行时长和单次任务 token 上限。
- 用户可见：展示当前阶段、已完成步骤、等待事项、中间结果和不确定点。
- 可中断：用户可以取消任务、补充信息或要求调整方向。
- 可恢复：工具失败、信息不足、审批等待或模型服务不可用时，应说明影响并给出恢复路径。
- 可追踪：关键计划、工具调用、知识访问、中间结果、失败和最终交付物应形成基础记录。
- 可降级：当任务超出能力、预算、权限或时间边界时，Agent 应缩小范围、请求确认、转人工或输出部分结果。
- 不绕权：复杂任务拆解、工具调用和专家 Agent 协作不得绕过用户、Agent、资源和租户边界。

### 10.4 复杂任务交付物要求

复杂任务的结果不应只是自然语言回答，而应尽量形成可直接使用或可继续流转的交付物。

项目助理 Agent 的 MVP 交付物至少包括：

- 会议纪要：会议结论、行动项、责任人、截止时间、风险点和待确认事项。
- 项目周报：本周进展、关键成果、延期阻塞、风险原因、下周计划和需协调事项。
- 风险分析：风险描述、依据、影响范围、严重程度、建议动作和待确认信息。
- 任务拆解：任务列表、优先级、依赖关系、负责人建议、时间建议和创建前确认项。

交付物应标注来源或依据；来源不足、判断不确定或信息冲突时，应明确说明。

### 10.5 工具调用失败

当工具调用失败或外部系统不可用时，Agent 应在合理范围内尝试恢复。无法恢复时，需要告知用户失败原因、影响范围和可选替代操作。

### 10.6 任务理解或计划不确定

当 Agent 对用户意图、任务范围或执行计划不确定时，应追问或请求确认，而不是贸然执行。

### 10.7 审批拒绝或超时

审批拒绝时，Agent 应读取拒绝原因并向用户说明受限动作无法继续。审批超时时，应按企业策略继续等待、终止任务、提醒审批人或建议用户转人工。

### 10.8 知识低可信

当知识召回结果不足、冲突或用户无权访问时，Agent 应明确说明无法给出可靠答案，并建议用户补充资料、换个问法、选择知识范围或转人工。

### 10.9 外部服务不可用

当模型、知识库、工具服务、渠道或审批服务不可用时，平台应向用户展示可理解的不可用提示，并避免反复消耗资源。

### 10.10 并发与冲突

当多个用户或任务对同一 Agent、同一资源或同一业务对象发起冲突操作时，平台应避免静默覆盖或重复执行，并提示用户确认、排队、取消或转人工处理。

### 10.11 部分完成

当任务已经部分完成但后续失败时，Agent 应说明已完成动作和可能影响。是否支持撤销、补发、重试或人工补偿，由具体业务能力决定。

## 11. 动态审批体验

动态审批用于处理“Agent 可以申请，但不能自动执行”的动作。

### 11.1 审批触发

审批请求应让审批人理解：谁发起、哪个 Agent 发起、要做什么、涉及哪些数据或资源、风险是什么、有效期多久、拒绝后会怎样。

### 11.2 审批路由

审批请求必须有明确接收人。审批人确定优先级如下：

1. 权限策略指定审批人：权限配置中已明确指定审批人的，按配置发送。
2. 资源所有者：涉及特定数据、工具或知识库时，发送给对应资源负责人。
3. Agent 业务负责人：以上规则未覆盖时，发送给 Agent 绑定的业务负责人。
4. 企业管理员兜底：所有规则无法匹配时，发送给企业管理员。

MVP 阶段至少支持 Agent 管理员在权限策略中指定审批人；未指定时默认发送给企业管理员。资源所有者自动匹配、组织架构路由和复杂审批工作台后续阶段建设。

### 11.3 审批通知

审批可以通过企业聊天工具、邮件或站内通知送达。渠道支持时，审批人可以在通知中直接通过、拒绝或填写原因。

### 11.4 审批拒绝

审批拒绝后，Agent 应停止对应受限动作，向用户说明拒绝原因或可公开的拒绝说明，并提供替代方案。

### 11.5 审批统计

平台需要统计审批数量、通过率、拒绝率、超时率和高频审批来源，用于优化权限策略和减少审批打扰。

MVP 阶段只做基础审批路由、审批通知和通过/拒绝处理；独立审批工作台、批量审批和复杂统计后续阶段建设。

## 12. 知识库绑定与知识可信

### 12.1 绑定关系

一个 Agent 可以绑定一个或多个知识库。Agent 管理员应能配置知识库用途、适用范围和是否允许在回答中展示来源。

### 12.2 权限约束

Agent 绑定知识库不代表用户自动获得全部知识访问权。用户通过 Agent 访问知识时，必须同时满足企业数据权限和 Agent 配置边界。

### 12.3 知识更新

知识库更新后，Agent 应有明确的生效规则。高风险知识变更可能需要重新验证或重新发布。

### 12.4 低可信兜底

当知识结果不可靠、来源不足或存在冲突时，Agent 应明确说明不确定性，不得编造结论。

### 12.5 来源展示

基于知识库回答时，Agent 应尽量展示来源或依据，帮助用户判断可信度。

## 13. 多 Agent 协作边界

### 13.1 MVP 范围

MVP 阶段只验证主 Agent 调用一个专家 Agent 的最小路径，用于证明平台未来具备 Agent 协作扩展方向。该能力不作为第一阶段核心交付闭环。

### 13.2 对外责任

对普通用户而言，主 Agent 是对外责任主体。即使内部调用了专家 Agent，最终结果仍由主 Agent 汇总和解释。

### 13.3 权限边界

多 Agent 协作不能绕过任一参与方的权限边界。任何参与方权限不足时，对应动作都不能继续执行，除非经过明确授权和审计。

### 13.4 委派约束

平台需要防止无限委派、循环委派、过宽委派和不可解释的多层委派。超出委派边界时，主 Agent 应提示用户拆分任务、降低范围或转人工。

### 13.5 Agent 发现与注册

后续阶段需要支持 Agent 注册、能力描述、适用场景、可见范围、调用条件和成本预估，使主 Agent 能发现合适的专家 Agent。MVP 阶段可由管理员预先配置协作关系，不做自动发现。

### 13.6 委派授权预留

后续需要支持受控委派授权：主 Agent 在明确范围、时间、资源和审计要求下，将本次任务所需的有限权限委派给专家 Agent。MVP 阶段只预留，不做完整能力。

## 14. Agent 版本与发布兼容

### 14.1 版本发布

Agent 的角色、职责、Prompt、工具、知识、权限、预算和渠道配置变化都应形成版本。用户和管理员应能看到当前使用的是哪个版本。

### 14.2 进行中任务

Agent 发布新版本时，不应强制打断正在进行的对话、任务和审批。进行中的任务应能保持上下文稳定，直到完成、取消或用户主动刷新。

### 14.3 待审批请求

待审批请求应保留发起时的上下文和配置说明。审批通过或拒绝时，用户和审批人应能理解该请求基于哪个版本发起。

### 14.4 定时和事件任务

版本更新可能影响定时任务和事件触发任务。发布前需要提示可能受影响的配置，并在必要时要求管理员确认。

### 14.5 回滚

回滚应影响后续新请求，不应破坏已完成任务记录和历史审计。回滚后，用户和管理员应能查看回滚原因和影响范围。

### 14.6 Agent 记忆

Agent 记忆跨版本使用时，应保证可理解、可追溯。版本变化导致记忆不适用时，应提示管理员处理或限制使用。

## 15. 数据隐私与生命周期

### 15.1 数据分类

平台需要分类管理对话数据、任务数据、审批数据、审计日志、Agent 记忆、知识访问记录、工具调用记录和反馈数据。

### 15.2 数据保留

平台需要支持租户级数据保留策略。不同类型数据可以有不同保留时长。涉及合规行业时，应允许企业按自身要求配置。

### 15.3 数据删除与脱敏

用户离职、账号禁用、Agent 停用或租户到期时，平台需要有明确的数据删除、归档或脱敏策略。审计日志中出现的密码、密钥、身份证号、薪资等敏感信息应脱敏。

### 15.4 访问记录

平台需要记录谁在什么时间通过哪个 Agent 访问了哪些知识、工具或业务资源，以满足安全审计要求。

### 15.5 MVP 要求

MVP 阶段至少需要支持基础数据保留配置、用户相关数据处理规则、Agent 停用后的数据处理规则和审计日志脱敏要求。

## 16. 成本控制要求

成本控制按阶段建设，需求文档保留完整方向，但 MVP 只做基础控制。

### 16.1 成本控制目标

平台需要让企业能设置预算、看到消耗、发现异常并阻止明显失控的任务。

### 16.2 MVP 成本能力

MVP 阶段支持：

- Agent 日预算；
- 单次任务 token 上限；
- 超限时拒绝继续执行或提示管理员处理；
- 基础成本统计；
- 基础告警。

### 16.3 后续成本能力

后续阶段扩展用户级预算、部门级预算、工具级预算、模型级预算、自动降级、成本审计、费用归属和智能预算建议。

### 16.4 用户提示

当用户触发明显高成本任务时，Agent 应提示任务可能消耗较高资源，并在必要时请求确认或管理员处理。

## 17. Agent 人设一致性

### 17.1 跨渠道一致性

同一 Agent 在不同渠道中的核心角色、职责和边界保持一致，差异只体现在消息展示和交互能力上。

### 17.2 跨会话一致性

同一用户再次使用同一 Agent 时，Agent 可以在授权范围内延续历史背景、任务偏好和上下文记忆。

### 17.3 企业品牌约束

平台应支持企业级语言风格、合规表达和内部沟通规范，避免 Agent 使用不符合企业要求的表达方式。

### 17.4 角色边界

超出职责范围的请求，Agent 应明确拒绝、解释原因，并在可能时推荐合适的 Agent、流程或人工渠道。

## 18. 功能范围

### 18.1 Agent 配置中心

支持项目助理 Agent 的最小配置，包括角色职责、边界、知识绑定、工具绑定、权限配置、预算配置、渠道配置和发布范围。后续扩展到 Agent 创建、模板创建、表单配置、白名单验证、回滚和生命周期管理。

### 18.2 能力中心

支持接入和管理项目助理 Agent 所需的基础知识、文档、内置工具和 HTTP/OpenAPI 工具。后续扩展事件触发、MCP、通用 Workflow、Agent Tool 和能力市场。

### 18.3 工具管理

支持工具注册、描述、启用停用、权限要求、风险等级、可用性检查和调用记录。

工具调用必须受平台策略约束。平台需要支持工具白名单、风险分级、调用前确认、动态审批、调用记录和异常拦截。高风险工具不得在原生系统中裸跑，应在受控执行环境或沙箱中运行，并限制可访问的文件、网络、命令、浏览器、企业资源和输出范围。

### 18.4 Agent 运行能力

支持会话处理、上下文使用、任务理解、复杂度判断、计划拆解、Dynamic Workflow、工具调用、知识查询、用户确认、审批等待、失败提示、自检和结果返回。

Agent 运行时必须保持角色、职责、权限和系统边界稳定，不应因用户输入、文件内容、URL 参数、知识库文本或其他外部内容而改变自身边界。平台需要具备基础运行时安全校验和 Prompt 注入风险识别能力。

### 18.5 任务与执行追踪

支持任务过程可见、执行计划展示、长任务跟踪、中间结果展示、等待事项提示、取消任务、失败记录、执行事件记录和基础历史查看。平台应将长任务作为可追踪、可恢复、可审计的工作单元管理，支持后续扩展完整任务账本、运行录制、问题复现和回归验证能力。具体状态设计在技术方案中定义。

### 18.6 权限与动态审批

支持用户权限、Agent 权限、资源权限、动态授权、审批路由、审批通知、审批结果处理、禁止执行和权限审计。

用户权限在对话或任务进行中发生变化时，平台不能静默忽略，也不能让用户无感知地继续执行敏感操作。新请求应按最新权限判断；进行中任务在后续涉及权限校验的动作时，应按最新权限判断，并向用户说明权限变化对任务的影响。

### 18.7 渠道接入

支持 Web Chat 和至少一个企业聊天渠道。后续扩展飞书、钉钉、企业微信、微信、QQ、Open API 和 Webhook。

渠道接入必须支持将渠道用户身份映射到平台用户身份。企业聊天渠道需要通过企业用户 ID 关联平台成员；Web Chat 需要通过企业登录认证关联平台用户。无法识别身份时，Agent 不应执行任何需要权限的操作，只能提供公开能力或引导用户完成身份绑定。同一用户跨渠道访问同一 Agent 时，权限、记忆和审计记录应统一归属。

MVP 阶段至少支持企业聊天渠道通过企业用户 ID 关联平台用户、Web Chat 通过企业登录认证关联用户，以及未知身份的受限处理。

### 18.8 多 Agent 协作预留

支持项目助理 Agent 在复杂任务中调用一个预配置专家 Agent 的最小验证路径。该能力服务于 Dynamic Workflow 的扩展验证，不作为 MVP 核心交付闭环。后续扩展 Agent 注册、搜索、自动匹配、委派授权、责任链和冲突处理。

### 18.9 知识与记忆中心

支持知识库绑定、来源展示、低可信提示、会话记忆、任务记忆、用户记忆、Agent 记忆和不同存储后端扩展。知识访问必须遵守租户、用户和 Agent 边界。

长期记忆不应由 Agent 无约束直接写入。平台需要支持记忆候选、策略判断、审核、晋升、冲突处理、合并和清理等治理要求。MVP 阶段只做基础记忆和存储适配，完整记忆治理闭环后续建设。

### 18.10 观测与审计

支持 Agent 运行记录、工具调用记录、审批记录、权限判断记录、失败记录、成本记录、知识访问记录和审计查询。

### 18.11 模型与 Prompt 管理

支持多模型接入方向、基础模型调用记录、Prompt 模板、Prompt 版本、Prompt 发布和回滚。平台应避免模型密钥分散在各 Runtime 或业务模块中，后续通过统一模型网关管理模型供应商、模型授权、调用密钥、调用账本和成本归属。模型路由、限流、降级等具体能力在技术方案和后续阶段细化。

### 18.12 成本治理

支持 Agent 预算、任务上限、基础成本统计和告警。多维预算、自动降级和完整成本审计后续阶段建设。

### 18.13 数据治理

支持多租户隔离要求、数据分类、数据保留、删除脱敏、访问记录和审计要求。

### 18.14 执行 Runtime 管控

平台应支持不同形态的 Agent 执行 Runtime，包括平台云端 Runtime、企业内网 Runtime、用户本地 Runtime 和专用任务 Runtime。

无论 Runtime 部署在哪里，都必须接受平台统一的身份认证、Agent 配置、权限策略、工具策略、审批策略、成本策略和审计要求。

Runtime 不应脱离平台独立获得企业资源访问权限。涉及企业知识、业务系统、高风险工具、外发消息、敏感数据、高成本模型或越权访问的动作，必须按照平台策略进行校验、确认或审批。

Runtime 执行工具、脚本、浏览器操作、文件访问、网络访问和企业系统调用时，不应直接在原生系统中裸跑。平台需要支持受控执行环境或沙箱化执行，限制 Runtime 可访问的目录、命令、网络、浏览器上下文、系统凭据和输出通道。沙箱逃逸、越权访问、敏感文件读取和未授权外发必须作为高风险行为处理。

低风险本地操作可以由 Runtime 基于平台下发的策略快速执行；高风险动作需要平台实时校验；越权或敏感动作进入动态审批；关键执行事件需要按风险等级同步或异步上报审计。

MVP 阶段优先支持平台侧或服务端 Runtime，并要求工具调用具备基础隔离和风险拦截。企业内网 Runtime、用户本地 Runtime、专用任务 Runtime、复杂 Runtime 注册治理和完整沙箱能力作为后续阶段建设。

## 20. 推荐样板场景

第一阶段推荐以“项目助理数字员工”作为样板场景。

原因：项目管理是企业高频场景，材料、会议、任务、风险和周报之间存在真实复杂工作链路，适合验证 Agent 是否能从“回答问题”升级为“完成工作”。该场景敏感度适中，也能验证知识查询、工具调用、Dynamic Workflow、任务进度、失败提示、确认、成本控制和基础审计。

MVP 样板能力：

- 项目知识问答；
- 会议纪要生成；
- 会议纪要转任务；
- 任务拆解建议和待确认事项；
- 调用 HTTP 工具创建或查询项目任务；
- 延期提醒；
- 周报生成；
- 项目风险分析；
- 复杂任务 Dynamic Workflow；
- 中间结果展示和最终结果自检；
- 需要权限时发起审批；
- 任务进度展示；
- 用户取消任务；
- 失败提示和反馈收集。

多 Agent 协作在 MVP 中只做最小 Demo，例如项目助理调用一个测试专家 Agent 获取测试风险建议，不作为核心交付闭环。

## 21. 演进路线

### 21.1 第一阶段：项目助理 Agent MVP

打通项目助理 Agent 的端到端执行闭环。重点验证复杂任务理解、Dynamic Workflow、知识和文档使用、HTTP/内置工具调用、会议纪要转任务、周报生成、风险分析、任务进度展示、用户确认、基础失败处理、Web Chat、一个企业聊天渠道和最小治理护栏。

### 21.2 第二阶段：多领域扩展

在项目助理 Agent 跑通后，扩展 HR、财务、客服、销售、研发等岗位 Agent 或模板。增强 Agent 配置中心、沙盒测试、审批工作台、多 Agent 协作、Agent Registry、委派约束、成本多维控制、用户反馈运营和事件触发。

### 21.3 第三阶段：生态与高级自治

建设 MCP Registry、Agent 市场、工具市场、通用 Workflow、目标驱动 Agent、自动优化、完整 FinOps、跨系统深度集成和受控跨租户共享，形成完整企业数字员工平台。

## 22. 关键风险与应对

### 22.1 Agent 执行价值不足

风险：第一版如果不能完成真实复杂工作，只是聊天问答或后台配置，用户不会形成持续使用意愿。

应对：MVP 必须以项目助理 Agent 的端到端交付物验收，包括会议纪要转任务、项目周报生成和项目风险分析。若 Agent 不能输出可直接使用的结果，平台管理能力不应作为成功标准。

### 22.2 MVP 过重

风险：第一版范围过大，导致交付周期拉长或质量不足。

应对：MVP 聚焦项目助理 Agent 执行闭环；多领域 Agent、完整创建发布平台、复杂灰度、完整成本、完整沙盒后置。

### 22.3 需求与技术边界混乱

风险：需求文档提前写实现方案，导致后续设计被过早锁死。

应对：需求文档只写产品行为和约束；状态机、权限计算、架构分工、接口和数据模型放到技术方案。

### 22.4 权限风险

风险：Agent 越权访问敏感数据或通过协作绕过权限。

应对：租户隔离、用户权限、Agent 边界、审批策略、禁止执行和审计追踪共同约束。

### 22.5 审批打扰

风险：审批人收到大量低价值审批请求。

应对：审批触发规则、禁止动态审批范围、审批统计和后续批量审批能力。

### 22.6 用户不信任

风险：用户不知道 Agent 在做什么、失败后无法理解，导致不敢使用。

应对：任务过程可见、失败原因可理解、用户可确认和取消、结果可反馈。

### 22.7 成本失控

风险：长任务、重复调用和异常重试导致费用不可控。

应对：MVP 支持 Agent 日预算、任务 token 上限、基础告警和超限保护，后续建设多维成本治理。

### 22.8 数据隐私与合规风险

风险：对话、任务、审批、知识访问和审计数据中包含敏感信息。

应对：数据分类、保留策略、删除脱敏、访问记录和审计要求纳入基础需求。

### 22.9 版本升级影响进行中任务

风险：Agent 新版本发布后破坏正在进行的对话、任务或审批。

应对：进行中任务保持上下文稳定，回滚不破坏历史记录，版本变化需要可追溯。

### 22.10 多 Agent 委派失控

风险：无限委派、循环委派、成本爆炸和责任不清。

应对：MVP 只做最小 Demo；后续建设委派边界、Agent 注册、可见性控制、成本约束和责任链。

### 22.11 Dynamic Workflow 失控

风险：复杂任务拆解过深、步骤过多、反复自检或无限补充信息，导致执行时间、成本和用户体验失控。

应对：Dynamic Workflow 必须限制步骤数、子任务数、执行时长和 token 上限；超出边界时应降级、请求确认、输出部分结果或转人工。

### 22.12 审批路由不清

风险：审批请求没有明确接收人，导致审批卡死、全部堆给企业管理员或无法匹配资源负责人。

应对：MVP 支持权限策略指定审批人和企业管理员兜底；后续支持资源所有者、业务负责人和组织架构路由。

### 22.13 跨渠道身份不一致

风险：同一用户在不同渠道中无法统一识别，导致权限判断失败、记忆割裂或审计无法追溯。

应对：渠道接入必须完成用户身份映射；未知身份只能使用公开能力或引导绑定。

### 22.14 运行时 Prompt 注入

风险：用户输入、文件、链接或知识内容诱导 Agent 改变角色、泄露系统指令或绕过权限。

应对：Agent 运行时必须保持角色和权限边界稳定，MVP 支持基础运行时安全校验和注入风险识别，后续在技术方案中细化防护机制。

### 22.15 执行 Runtime 脱管

风险：企业内网 Runtime 或用户本地 Runtime 如果脱离平台独立运行，可能绕过权限、审批、成本和审计要求，导致本地工具、企业资源和敏感数据失控。

应对：所有 Runtime 都必须作为平台受控执行节点运行。低风险动作可基于平台策略快速执行，高风险动作必须经过平台校验或审批，关键事件必须按风险等级上报审计。MVP 不建设完整本地 Runtime，但需求预留统一管控原则。

### 22.16 原生系统裸跑风险

风险：Agent 如果直接在原生系统中执行脚本、命令、文件访问、浏览器操作或网络访问，可能误删文件、读取密钥、泄露敏感数据、访问未授权系统或被恶意输入诱导执行危险动作。

应对：Runtime 工具执行必须优先进入受控执行环境或沙箱，限制文件、网络、命令、浏览器上下文、系统凭据和输出通道。MVP 阶段至少要求基础隔离、风险拦截和调用记录；完整沙箱能力后续建设。

### 23.6 Agent-first 方向修正

本文档根据产品方向重新收敛：第一阶段不再以完整企业数字员工平台后台为主线，而是以项目助理 Agent 的端到端执行价值为主线。平台化能力不删除，但从 MVP 主线调整为最小护栏、链路预留和后续演进规划。

本次修正重点包括：

| 调整项 | 处理结果 |
|---|---|
| 产品定位 | 调整为 Agent-first、Platform-ready，先验证可执行数字员工，再演进为企业平台 |
| MVP 范围 | 从创建发布、运行执行、治理三个平台闭环，调整为项目助理 Agent 复杂工作执行闭环 |
| 核心场景 | 将项目助理 Agent 处理复杂任务、会议纪要转任务、项目周报生成和项目风险分析作为第一阶段主场景 |
| Dynamic Workflow | 纳入复杂任务执行机制，明确其是内部执行模式，不是流程画布或大规模 Swarm |
