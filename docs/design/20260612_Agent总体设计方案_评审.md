# Agent 总体设计方案评审报告

> 评审对象：`docs/design/20260612_Agent总体设计方案.md`
> 参照基线：`docs/req/20260604_企业数字员工平台_需求.md`
> 评审角色：Agent 架构专家
> 评审日期：2026-06-12

---

## 一、总体评价

### 1.1 设计完成度评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 架构分层 | ★★★★☆ | Agent / Runtime / Context / Memory / Tool / Collaboration / Governance 七层清晰，职责边界合理 |
| 场景覆盖 | ★★★☆☆ | 两个落地场景有描述但落地路径模糊，与需求文档 MVP 场景存在错位 |
| 参考分析 | ★★★★★ | Claude Code / Codex / OpenClaw 三方对照扎实，取舍结论可靠 |
| Runtime 设计 | ★★★☆☆ | Run Loop 概念正确，但状态机、错误处理、长任务模型缺失 |
| 工具设计 | ★★★★☆ | ToolExecutor 抽象、CLI 安全、Schema 校验、调用链路完整 |
| Memory 设计 | ★★★★☆ | 分层合理，写入策略谨慎，但与需求中的知识可信机制缺少衔接 |
| 多 Agent 协作 | ★★★☆☆ | 对象定义完整，但缺少反馈回路、错误传播和退回重做机制 |
| 治理设计 | ★★★☆☆ | 原则正确，但 ModelGateway 缺失、Prompt 注入防御、成本执行机制空白 |
| 可观测性 | ★★☆☆☆ | RunStep + ToolCallLog 有定义，但无统一 trace、无实时监控、无问题定位能力 |

### 1.2 核心结论

**方案架构方向正确，抽象层次合理，参考分析质量高。但作为面向两个落地场景的设计方案，存在三类关键问题：**

1. **与需求文档 MVP 场景错位**——设计聚焦"敏捷开发团队"和"业务系统 CLI Agent"，但需求 MVP 是"项目助理 Agent"。这不是名称问题，是场景驱动的功能优先级和边界定义不同。
2. **Runtime 的"失败态"几乎空白**——正常路径完整，异常路径（重试、降级、退回、部分完成、超时）无设计。
3. **ModelGateway 是空白章节**——架构图中的核心节点，全文无专门设计。

## 二、场景覆盖评审

### 2.1 场景一：完整敏捷开发团队 Agent

| 评估项 | 覆盖情况 | 差距 |
|--------|---------|------|
| 角色定义 | ✅ Orchestrator / Product / Architect / Developer / QA / Delivery 六角色定义完整 | — |
| 协作流程 | ⚠️ 单向流水线有描述 | 缺少下游退回上游的反馈回路（§10.2 只有正向流） |
| Handoff | ✅ 结构化 Handoff 定义清晰 | — |
| QualityGate | ⚠️ 提到了质量门禁 | 缺少"不通过怎么办"的处理策略 |
| AgentThread | ✅ 绑定 TaskRun，字段完整 | — |
| 长时任务执行 | ❌ 无设计 | 敏捷团队从需求到交付可能持续数小时/数天，无异步执行、持久化 checkpoint、事件通知机制 |
| 资源隔离 | ⚠️ "读多写少可并行，写操作串行化"原则正确 | 未定义并发控制的具体机制（锁、队列、乐观/悲观） |
| 错误传播 | ❌ 无设计 | 某角色失败后，整组任务怎么处理？局部重试还是整组回滚？ |

**判定：框架可支撑，但长时任务执行模型和错误传播机制必须补齐，否则敏捷团队场景无法真正落地。**

### 2.2 场景二：业务系统 CLI / 插件化 Agent

| 评估项 | 覆盖情况 | 差距 |
|--------|---------|------|
| CLI 工具安全 | ✅ 白名单、参数模板、JSON schema、超时、脱敏、dry-run 设计完整 | — |
| ToolExecutor 抽象 | ✅ CLI / HTTP / Java / MCP 执行器抽象合理 | — |
| PluginManifest | ✅ 插件打包单位定义清晰 | — |
| 写操作审批 | ✅ 审批和恢复机制有描述 | — |
| 幂等控制 | ⚠️ 提到了 idempotency key | 未定义 key 生成规则、存储时效和冲突处理 |
| 工具发现与路由 | ⚠️ capabilityTags 有定义 | 缺少 Agent 如何根据用户意图从工具池中选择合适工具的匹配策略 |

**判定：场景二覆盖度较高，Tool 层设计是方案中最扎实的部分。幂等和工具匹配需细化。**

### 2.3 需求文档 MVP 场景对照

| 需求 MVP 能力（需求文档章节） | 设计文档覆盖 | 评估 |
|---|---|---|
| **Dynamic Workflow 复杂任务执行**（§5.1, §10.2） | §5.2 提到 `dynamic_workflow` 模式 | ⚠️ 只有模式名和选择规则，无执行细节：怎么拆步骤、怎么合并中间结果、怎么自检、怎么降级 |
| **会议纪要转任务**（§5.2） | 未提及 | ❌ 场景未体现 |
| **项目周报生成**（§5.3） | 未提及 | ❌ 场景未体现 |
| **项目风险分析**（§5.4） | 未提及 | ❌ 场景未体现 |
| **知识库绑定与来源展示**（§12） | Tool 类型中提到 `knowledge` | ❌ 知识库不是普通工具，它有独立的绑定关系、权限约束、可信判断和来源展示，当前设计把它降格为一种 Tool 类型是不够的 |
| **低可信兜底**（§12.4） | 未设计 | ❌ 需求明确要求知识冲突/不足时不能编造 |
| **一句话创建 Agent 草稿**（§7.1） | §4.1 只定义了 AgentDefinition 字段 | ❌ 无创建流程、草稿生成、表单配置和发布验证的设计 |
| **Agent 最小表单配置**（§7.3） | 未设计 | ❌ |
| **发布验证与白名单**（§7.4, §7.5） | 未设计 | ❌ |
| **动态审批路由**（§11） | §11 Governance 提到 Approval | ⚠️ 只提到"高风险动作审批"，未设计审批路由规则（指定审批人 → 资源所有者 → 业务负责人 → 管理员兜底） |
| **任务过程可见**（§9.2） | §5.3 RunStep 有定义 | ⚠️ RunStep 定义了内部数据结构，但未设计用户可见的展示模型（阶段、进度、等待事项） |
| **用户确认与取消**（§9.3） | §11.2 Checkpoint 提到 `user_input` 类型 | ⚠️ 取消后的影响说明和部分完成处理未设计 |
| **错误展示**（§9.4） | 未设计 | ❌ 需求要求业务可理解的失败原因和可选下一步，设计无此模型 |
| **渠道适配与身份映射**（§18.7） | 架构图有 User/Channel，但无专门设计 | ❌ Web Chat + 企业聊天渠道的用户身份映射、未知身份处理是 MVP 必做项 |
| **Agent 人设跨渠道一致**（§17） | rolePrompt 存在 | ⚠️ 只靠 rolePrompt 无法保证跨渠道一致，需要平台层强制 |
| **Prompt 注入防护**（§22.14） | 未设计 | ❌ 需求 MVP 要求基础运行时安全校验和注入风险识别 |
| **成本控制**（§16） | Governance 提到 Budget | ⚠️ 无具体机制设计：日预算怎么扣、超限怎么拦截、token 怎么计 |
| **数据保留与脱敏**（§15） | 未设计 | ❌ |
| **反馈收集**（§9.6） | 未设计 | ❌ |

**MVP 场景覆盖判定：约 40% 的需求 MVP 必做项在本设计文档中无对应设计。**

## 三、关键缺陷（影响架构根基）

### 缺陷 1：ModelGateway 是空白章节

**位置**：§3 架构图中有 ModelGateway 节点，全文无专门章节

**影响**：Agent 系统中模型调用的复杂度不亚于工具调用。缺乏 ModelGateway 设计意味着：
- 模型路由（不同任务用不同模型）无法实现
- 主模型挂了无法降级
- Token 预算无法在模型调用层强制执行
- 多供应商的 prompt 格式差异无法屏蔽
- 流式调用中断无法恢复
- 模型调用成本无法归集

**对标需求**：需求 §18.11 明确要求"统一模型网关管理模型供应商、模型授权、调用密钥、调用账本和成本归属"。

**对标已有技术方案**：`docs/design/20260604_企业数字员工平台_技术.md` §6.6 已经有 ModelGateway 的职责定义和 OpenAI 兼容接入设计。本设计文档应该继承并扩展，而不是留空。

**建议**：补一个与 Tool 层同等规格的 ModelGateway 章节，至少覆盖：
1. 模型路由策略（按任务类型、Agent 配置、成本预算选择模型）
2. 降级与容错（主模型不可用时的 fallback 链）
3. Token 预算执行（在模型调用前校验剩余预算）
4. 流式处理（SSE / WebSocket 流式输出和中断恢复）
5. 多供应商适配（OpenAI / Anthropic / 本地模型的统一接口）
6. 调用日志与成本归集

---

### 缺陷 2：Runtime 长时任务执行模型缺失

**位置**：§5 Agent Runtime 设计

**问题**：方案的 Run Loop 描述偏向"同步短任务"，没有区分短任务和长任务的执行模型。敏捷团队从需求到交付可能持续数小时甚至数天。

缺失项：
1. **异步执行**：长任务不能阻塞调用线程，需要异步提交 + 事件通知
2. **持久化 checkpoint**：内存中的 checkpoint 不够，需要持久化到数据库，支持进程重启后恢复
3. **用户断连恢复**：用户关闭浏览器后重新打开，应能看到任务进度并继续交互
4. **进度推送**：Websocket / SSE / 轮询机制
5. **超时管理**：长任务的总超时和单步骤超时

**对标需求**：需求 §10.3 明确要求 Dynamic Workflow "可恢复"，§18.5 要求"长任务作为可追踪、可恢复、可审计的工作单元管理"。

**对标已有技术方案**：`docs/design/20260604_企业数字员工平台_技术.md` §5.1 RuntimeGateway 已经定义了 `startRun` / `cancelRun` / `resumeRun` / `streamEvents` 接口，且 §5.3 定义了完整的 RuntimeEvent 体系。本设计文档应该在此基础上定义 Agent 层面的长时任务执行语义。

**建议**：
1. 在 §5 Runtime 中明确区分"同步执行模式"（direct_tool / single_agent 简单任务）和"异步执行模式"（dynamic_workflow / multi_agent 复杂任务）
2. 定义 AgentRunEngine 对 Checkpoint 的持久化策略
3. 定义用户断连后的 Session 恢复机制
4. 定义进度推送的事件类型和渠道

---

### 缺陷 3：错误处理和失败恢复策略缺失

**位置**：全文

**问题**：方案描述了"正常路径"，但错误处理几乎是空白。

| 失败场景 | 当前方案 | 需求要求（章节） |
|----------|---------|-----------------|
| 工具调用失败 | 未描述 | Agent 应在合理范围内尝试恢复，无法恢复时告知原因和替代操作（§10.5） |
| 模型返回无效响应 | 未描述 | 外部服务不可用时展示可理解提示（§10.9） |
| 审批拒绝 | §11 Governance 提到 approval | 应读取拒绝原因并向用户说明受限动作无法继续（§10.7） |
| 审批超时 | 未描述 | 按企业策略继续等待、终止或提醒审批人（§10.7） |
| 知识低可信 | 未描述 | 明确说明无法给出可靠答案（§10.8） |
| 上下文超窗口 | "摘要或丢弃" | 需要裁剪优先级表（§10.3 可降级） |
| 多 Agent 协作中某个 AgentThread 失败 | 未描述 | 应说明已完成部分和可能影响（§10.11） |
| 部分完成 | 未描述 | 应说明已完成动作和可能影响（§10.11） |
| 并发冲突 | 未描述 | 避免静默覆盖或重复执行（§10.10） |

**建议**：补一个"错误与异常处理"章节，至少覆盖：
1. 重试策略（次数、退避、条件）
2. 降级路径（缩小范围 → 请求确认 → 部分结果 → 转人工）
3. 多 Agent 退回重做机制
4. Context 裁剪优先级表
5. 审批拒绝 / 超时的处理策略
6. 部分完成的影响说明模型

---

### 缺陷 4：状态机不完整

**位置**：§5.3 RunStep

**问题**：RunStep 定义了 9 种类型和 5 种状态，但没有定义合法状态转换。TaskRun、AgentThread、CollaborationSession 同理。

没有状态机约束的实现风险：
- 非法状态转换（如 `completed → running`）无法在代码层拦截
- 前端无法基于状态决定展示逻辑
- 恢复机制无法判断从哪个状态恢复到哪个状态

**建议**：为每个核心对象补一张状态转换图，至少包括：

```
TaskRun: created → running → completed
                         → failed
                 → suspended → resuming → running
                             → cancelled
                             
RunStep: pending → running → completed
                         → failed
                 → suspended → resuming → running
                             
AgentThread: created → running → completed
                              → failed
                      → suspended → resuming → running
                                  → cancelled
                                  
CollaborationSession: created → planning → executing → completed
                                                  → failed
                                          → suspended → resuming
                                                      → cancelled
```

## 四、重要设计缺口

### 缺口 1：知识库应作为一等概念，而非工具的一种

**位置**：§8.1 Tool 类型中 `knowledge` 作为一种 Tool 类型

**问题**：需求文档 §12 花了一整章定义知识库的绑定关系、权限约束、可信判断、来源展示和低可信兜底。知识库在 Agent 系统中的角色远超普通工具：

| 维度 | 普通工具 | 知识库 |
|------|---------|--------|
| 绑定粒度 | Agent 级 | Agent 级 + 用户权限级 |
| 权限判断 | Agent 是否可用 | Agent 可用 + 用户是否有权访问该知识 |
| 结果可信度 | 工具执行成功/失败 | 高/中/低/冲突/不足 |
| 来源展示 | 不需要 | 必须展示来源和依据 |
| 低可信处理 | 失败即停 | 明确说明不确定性，不编造 |
| 对 Agent 行为影响 | 调用/不调用 | 影响回答语气、置信度和建议 |

**建议**：
1. 知识检索应有独立的 `KnowledgePolicyJson`，不混入 `toolPolicyJson`
2. Context 构建流程中知识来源应有独立处理逻辑（可信评估、来源标记、低可信提示）
3. 增加知识可信度评估模型：`high / medium / low / conflicting / insufficient`
4. 增加知识来源展示格式定义

---

### 缺口 2：Prompt 注入防御缺失

**位置**：无专门章节

**问题**：需求 §22.14 明确要求"Agent 运行时必须保持角色和权限边界稳定，MVP 支持基础运行时安全校验和注入风险识别"。已有技术方案 §9.2 也定义了 Prompt 注入防护的 MVP 和后续阶段。

Agent 系统面临的注入风险更高：
- 用户输入恶意指令覆盖 Agent 角色
- Tool 返回内容包含注入（查询结果嵌入"忽略之前指令"）
- 跨 Agent Handoff 内容被污染
- 知识库文档中包含注入指令

**建议**：在 §11 Governance 中补一个"运行时安全"子节，至少包括：
1. 输入标记分离（`<user-input>` 标签，明确告诉模型这是不可信内容）
2. Tool 输出不可信标记
3. Handoff 内容校验
4. Agent 角色边界强制（Runtime 在每轮循环开始时重新注入 rolePrompt，不受对话历史影响）
5. 高风险输出二次确认

---

### 缺口 3：Agent 创建 / 配置 / 发布流程未设计

**位置**：§4 Agent 定义只有字段定义

**问题**：需求 §7 花了一整章定义 Agent 的创建方式（一句话 / 模板 / 空白）、草稿生成、表单配置、发布验证和白名单管理。设计文档只定义了 `AgentDefinition` 的数据字段，没有创建流程、草稿生成策略、表单校验规则和发布流程。

这是 MVP 必做项（需求 §19.2），不是后续能力。

**建议**：补一个"Agent 生命周期管理"章节：
1. 创建流程（输入 → 草稿生成 → 表单确认 → 校验 → 发布）
2. 草稿生成策略（基于角色 Prompt 生成默认配置）
3. 发布验证清单（配置完整性、工具可用性、知识绑定、Prompt 版本）
4. 白名单管理（指定用户可见可用）
5. 版本管理（配置变更 → 新版本 → 发布 → 回滚）

---

### 缺口 4：可观测性设计薄弱

**位置**：§5.3 RunStep + §8.4 ToolCallLog

**问题**：需求 §18.5 要求"长任务作为可追踪、可恢复、可审计的工作单元"，§18.10 要求完整的观测与审计能力。当前设计只有 RunStep 和 ToolCallLog，缺少：

1. **统一 traceId**：无法把 CollaborationSession → TaskRun → AgentThread → RunStep → ToolCallLog 串起来
2. **实时监控**：Agent 卡住了怎么发现？超时告警？
3. **问题定位**：用户说"结果不对"，怎么复现那一次运行的完整上下文？
4. **用户可见的进度模型**：RunStep 是内部数据结构，用户看到什么？

**对标已有技术方案**：`docs/design/20260604_企业数字员工平台_技术.md` §5.3 定义了完整的 RuntimeEvent 体系，每个事件都带 `traceId`。本设计文档应该继承这个能力。

**建议**：
1. 定义 `traceId` 贯穿所有执行对象
2. 定义用户可见的"执行时间线"模型（区别于内部 RunStep）
3. 定义超时检测和告警机制
4. 定义运行回放所需的最小数据集

---

### 缺口 5：多 Agent 协作缺少反馈回路

**位置**：§10.2 敏捷开发团队协作流

**问题**：当前是单向流水线：

```
Product → Architect → Developer → QA → Delivery
```

但实际场景中：
- QA 发现设计不合理，需要退回 Architect
- Developer 发现 PRD 矛盾，需要退回 Product
- Architect 发现技术方案与约束冲突，需要退回 Product 修改需求

**建议**：
1. 在 CollaborationPlan 中增加 `reworkPolicy`：最大重做次数、退回条件、升级策略
2. 在 Handoff 中增加 `reworkFrom` 和 `reworkReason` 字段
3. QualityGate 增加 `pass` / `rework` / `escalate` 三种结果

---

### 缺口 6：用户交互层设计缺失

**位置**：无专门章节

**问题**：需求 §9 花了一整章定义消息类型（文本 / 卡片 / 确认 / 进度 / 文件 / 反馈）、错误展示、渠道适配和反馈收集。设计文档完全没有用户交互层设计。

对于 Agent 产品来说，用户交互不是前端的事——它需要 Runtime 和后端输出结构化的事件和消息，前端只负责渲染。

**建议**：补一个"用户交互模型"章节，定义：
1. Agent 输出消息的结构化类型（text / card / confirmation / progress / file / feedback_request）
2. 错误展示模型（失败原因 + 影响范围 + 可选下一步）
3. 进度展示模型（当前阶段 / 已完成 / 等待中 / 下一步）
4. 确认与取消的消息协议

### 缺口 7：成本控制无执行机制

**位置**：§11 Governance 提到 Budget

**问题**：需求 §16 要求"Agent 日预算、单次任务 token 上限、超限拒绝继续执行"。设计文档只在 Governance 表格里提了一行"Budget"，没有回答：
- 预算在哪一层扣减？（模型调用前？工具调用前？RunStep 完成后？）
- Token 消耗怎么统计？（模型返回的 usage？Runtime 估算？）
- 超限时当前步骤怎么处理？（立即终止？等当前步骤完成后终止？）
- 日预算的"日"怎么界定？（自然日？滚动 24 小时？）

**建议**：在 Governance 章节补一个"预算执行策略"子节，明确：
1. 预算检查点（模型调用前、工具调用前、每个 RunStep 完成后）
2. 扣减方式（模型返回的 usage 为主，工具调用估算为辅）
3. 超限行为（拒绝新步骤 / 终止当前运行 / 降级 / 请求确认）
4. 预算周期（Agent 日预算按自然日重置）

### 缺口 8：渠道与用户身份未设计

**位置**：架构图有 User/Channel，但无专门设计

**问题**：需求 §18.7 要求"Web Chat 和至少一个企业聊天渠道"，且必须完成用户身份映射。这是 MVP 必做项。设计文档完全没有涉及：
- 渠道类型和接入方式
- 渠道用户身份到平台用户的映射
- 未知身份的受限处理
- 跨渠道的会话/记忆统一

**建议**：补一个"渠道与身份"章节，至少定义：
1. Channel 抽象（type / config / identityMapping）
2. 身份映射策略（企业用户 ID → 平台用户）
3. 未知身份的权限范围
4. 渠道消息适配（Web Chat 完整交互 vs 企业 IM 简化卡片）

## 七、平台化演进评估

### 7.1 平台化预留充分度

| 平台化方向 | 预留情况 | 评估 |
|-----------|---------|------|
| 多租户隔离 | 多处提到 scopeType/scopeId | ⚠️ 分散在各 Policy JSON 中，缺少统一的租户隔离层设计 |
| 多 Agent 模板 | §4.3 能力画像可配置 | ✅ 能力画像设计灵活 |
| 插件市场 | §9 Plugin 有优先级和来源 | ✅ 本地 manifest 可扩展为市场 |
| MCP 工具生态 | §8.1 列为 toolType | ⚠️ 无 MCP 协议适配设计 |
| 全渠道接入 | 无 | ❌ 缺少渠道抽象层 |
| 完整审计后台 | §11 提到 Audit | ⚠️ 无审计查询和分析模型 |
| 完整成本 FinOps | §11 提到 Budget | ⚠️ 无成本归集和分摊模型 |
| Runtime 分布式部署 | 无 | ❌ 已有技术方案有 RuntimeGateway，本设计未继承 |
| 多 Agent Registry | §10 提到 AgentThread | ⚠️ 无 Agent 发现和注册机制 |
| 事件触发 | 无 | ❌ 无事件抽象和触发机制 |

### 7.2 平台化最大风险

当前设计最大的平台化风险是**缺少统一的身份和权限抽象层**。

需求的权限模型是三层：
1. 用户权限（这个人能访问什么）
2. Agent 权限（这个 Agent 能做什么）
3. 资源权限（这个数据/工具/知识谁能用）

设计文档把权限分散在 `toolPolicyJson`、`contextPolicyJson`、`memoryPolicyJson` 中，缺少一个统一的权限评估模型。当平台化扩展到多租户、多渠道、多 Agent 协作时，分散的权限判断会导致：
- 跨租户越权难以全局拦截
- 多 Agent 协作时的权限传递难以追踪
- 审批路由缺少统一的主体判断

**建议**：补一个"权限评估模型"，定义 `PermissionCheck(actor, action, resource, context) → allow / deny / ask` 的统一判断入口。各 Policy JSON 是这个判断的输入，而不是独立的权限判断。

## 八、评审结论与建议

### 8.1 总体判定

**方案架构方向正确，核心抽象合理，但作为可进入技术实现的设计文档，完整度不足。**

核心问题排序：

| 优先级 | 问题 | 影响 |
|--------|------|------|
| P0 | ModelGateway 空白 | Agent 无法调用模型，系统不可运行 |
| P0 | 错误处理和失败恢复缺失 | Agent 失败后不可恢复，不可解释 |
| P0 | 与已有技术方案的关系不清晰 | 实现时出现两套抽象 |
| P1 | Runtime 长时任务执行模型缺失 | 敏捷团队场景无法落地 |
| P1 | 状态机不完整 | 实现质量无法保证 |
| P1 | 知识库不是一等概念 | 项目助理 MVP 的核心能力无设计支撑 |
| P1 | MVP 场景覆盖不足 40% | 设计与需求脱节 |
| P2 | Prompt 注入防御缺失 | 安全风险 |
| P2 | Agent 创建/配置/发布流程未设计 | MVP 必做项无设计 |
| P2 | 用户交互层缺失 | 产品体验无设计支撑 |
| P2 | 可观测性薄弱 | 问题无法定位 |
| P2 | 成本控制无执行机制 | 预算失控风险 |

### 8.2 建议修改策略

不建议推倒重来。方案的架构方向和核心抽象（AgentDefinition / ContextPackage / ToolExecutor / Handoff）都是正确的。

建议分两步：

**第一步：补齐 P0 和 P1 项（必须在进入实现前完成）**

1. 补 ModelGateway 章节（继承已有技术方案 §6.6）
2. 补错误处理和失败恢复章节
3. 明确与已有技术方案的继承关系
4. 补长时任务执行模型（继承已有技术方案 RuntimeGateway）
5. 补状态机定义
6. 提升知识库为一等概念
7. 补 MVP 场景设计（Dynamic Workflow 执行细节、项目助理场景路径）

**第二步：补齐 P2 项（可与实现并行）**

1. 补运行时安全（Prompt 注入防御）
2. 补 Agent 生命周期管理
3. 补用户交互模型
4. 补可观测性和 trace
5. 补成本控制执行机制
6. 补渠道与身份设计
