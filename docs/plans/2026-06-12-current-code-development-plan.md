# 2026-06-12 现存代码梳理与开发计划

依据：`docs/design/20260612_Agent总体设计方案.md`。

## 0. 2026-06-14 状态修订

本轮继续按“两大落地场景”收敛：完整敏捷多 Agent 团队、业务系统 CLI/HTTP 插件化 Agent。最新代码已经补齐以下关键点：

- 协作计划提交阶段会提前校验 `stage.agentVersionId` 与 `stage.toolCalls[]` 的工具范围是否匹配。若工具不在 AgentVersion 的 `toolScopeJson` 中，计划直接标记 `validationStatus=failed`，避免等到 Runtime 执行时才出现 `TOOL_DENIED`。
- 协作计划提交阶段同时校验 `toolCalls[]` 对应工具是否已注册、是否 active、以及声明的 `toolCode` 是否与 `toolId` 对应的 ToolConfig 一致，业务插件/手写计划的工具配置错误会前置暴露。
- `toolCalls[]` 必须搭配 `createTask=true` 和 `agentVersionId` 使用，且 `createTask=true` 必须声明 `agentId`；否则工具链不会进入绑定 Task input，或无法拿到运行时工具范围快照，现在会在计划提交阶段失败。
- 协作页已展示 `validationResultJson.errors`，用户能直接看到工具范围不匹配、工具不存在、版本不存在等计划校验失败原因。
- 审批通过后的恢复链路已由测试锁定：`resumeTask` 会发布 `running/resume` 和 `completed/runtime_completed` 两次任务状态事件，协作线程监听器可据此把线程从 suspended 同步到 completed。
- Runtime 召回 confirmed memory 时已兼容协作线程 Task input 中的 `collaborationContext.sessionId`，因此 `memoryPolicy.scopes=["session"]` 可以拿到会话级记忆，不再依赖顶层 `sessionId`。
- 前端已新增 `/collaboration` 协作会话创建入口，导航不再硬编码到 `/collaboration/1`；用户可以输入目标、选择编排策略并创建真实会话，成功后进入 `/collaboration/{sessionId}` 继续提交计划和启动团队协作。
- CLI/HTTP 工具入参 schema 校验已补齐常用业务约束：`pattern`、`format(date/date-time/email/uri)`、`uniqueItems`、`minProperties/maxProperties`、嵌套 object/array、数组 item 级格式校验，以及 `oneOf/allOf` 组合 schema，降低业务系统工具被非法参数调用的风险。
- Task Artifact metadata 已补最小 producer/version 审计字段：`artifactVersion`、`producerAgentId`、`producerAgentVersionId`、`collaborationSessionId`、`stageCode`；协作线程同步输出产物时会选择最新 artifact ID，减少多产物时的交接歧义。
- 工具越权审计页已增加 Task 详情链接和 AgentVersion 工具范围修复入口；`ExistingAgentVersionToolsCard` 支持从 `/agent-config?agentId=...&versionId=...` 预填目标版本，方便从 `TOOL_DENIED` 审计事件回到草稿工具范围修复。
- QualityGate 失败分支已补最小闭环：required gate fail 后会把协作会话置为 `blocked`，并定位 `currentStageCode` 到失败 gate 所属 stage；计划可通过 `reworkStageCode` 指向返工 stage 自动创建返工线程，计划校验会拒绝不存在的 `reworkStageCode`；协作页下一步提示会优先展示 failed gate 和 failReason。
- PluginManifest 来源完整性已补最小审计：导入时计算 manifest `sha256`，在 `plugin_manifest.manifestJson._audit` 和工具 `authConfigJson._plugin` 中记录 `pluginCode/pluginVersion/manifestHash`；后端响应和前端 Manifest 卡片可展示短 hash，便于追溯业务工具来源和插件版本。
- `orchestrated_team` 的下一阶段 `autoStartTask=true` 已有代码和集成测试覆盖，并非仍然缺失；剩余重点应改为 Artifact 版本引用审计、完整团队角色模板和端到端场景数据。

因此，后续计划中“尚未自动启动下一阶段 TaskRun”的描述按当前代码状态视为过期，应以本节为准。

## 1. 总体判断

| 方向 | 当前判断 | 原因 | 处理 |
|---|---|---|---|
| 项目助理 Agent MVP | 可以作为第一阶段主线落地 | 已有 Agent、Task、Runtime、ModelGateway、Knowledge、Tool、Approval、前端工作台 | 继续补齐运行闭环和交付物质量 |
| 业务系统 CLI / 插件化 Agent | 架构底座可复用，最小工具/插件链路已打通 | ToolConfig、ToolCallLog、Policy、CliToolExecutor、PluginManifest、schema 最小校验已有 | 第二阶段继续补业务插件封装、权限和版本治理 |
| 完整敏捷开发团队 Agent | 仍作为第三阶段推进 | Collaboration 元模型已有，已具备显式创建绑定 Task 的最小桥接，但还没有完整多 Agent 阶段推进 | 保留现有代码，后续接 Runtime 编排 |
| Dynamic Workflow | 应作为执行模式之一，不作为所有任务默认入口 | 设计文档已明确 simple/direct/single/dynamic/multi-agent 分层 | 项目助理复杂任务先用最小动态步骤 |
| 平台性后台 | 当前不作为主线 | 会分散 MVP | 暂缓新增大后台能力 |
